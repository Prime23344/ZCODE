### Key Architecture Decisions

1. **Database**: SQLite via Prisma ORM for local dev (switchable to PostgreSQL for production by changing the `DATABASE_URL` in `.env`)
2. **Auth**: JWT with phone + OTP (mock OTP in dev — prints to server console)
3. **Payments**: Abstract `PaymentProvider` interface with `MPesaProvider` implementation using sandbox mode by default
4. **Real-time**: Socket.IO for admin activity feed and booking status updates
5. **i18n**: i18next with JSON locale files from day 1
6. **Currency**: All monetary values stored as `{ amount: Int, currencyCode: String }` — no hardcoded KES
7. **Country**: Every entity (users, categories, bookings) includes a `countryCode` field

### Database Schema (Prisma) — 18 models
- **User**: id, phone, email, role (CUSTOMER/PROVIDER/ADMIN), countryCode, createdAt
- **Provider**: userId (1:1), bio, location, county, averageRating, responseTime, verificationStatus, verificationRejectionReason
- **VerificationDocument**: id, providerId, documentType, issuingCountry, fileUrl, uploadedAt
- **ServiceCategory**: id, name, countryCode, icon, isActive
- **ProviderCategory**: providerId + categoryId (many-to-many)
- **Booking**: id, customerId, providerId, categoryId, status (11-state lifecycle), description, location, scheduledAt, country, currency, quoteAmount, quoteDuration, commissionRate, totalAmount
- **BookingMessage**: id, bookingId, senderId, content, createdAt
- **Payment**: id, bookingId, amount, currencyCode, status (escrow/released/refunded/partial), providerPayoutAmount, commissionAmount
- **Review**: id, bookingId, customerId, providerId, rating, text, providerResponse, createdAt
- **Dispute**: id, bookingId, openedById, reason, status, resolutionType, adminNotes, createdAt
- **DisputeEvidence**: id, disputeId, fileUrl, uploadedBy
- **SupportTicket**: id, userId, subject, description, status, adminResponse, createdAt
- **ActivityLog**: id, type, actorId, metadata (JSON), createdAt (drives admin feed)
- **PortfolioPhoto**: id, providerId, fileUrl, caption
- **OTPRecord**: id, userId, code, purpose, expiresAt (mock OTP in dev)
- **PasswordHash**: id, userId, hash (future-proof for email login)

### Implementation Phases (15 phases)

**Phase 1: Scaffolding** — Monorepo init (npm workspaces), Prisma schema with all 18 models, shared TS types, `.env.example` files, base tsconfigs

**Phase 2: Backend Auth & User Management** — Express server setup, JWT middleware, phone+OTP login (mock mode), user CRUD, role-based access, rate limiting

**Phase 3: Backend Categories & Search** — Service category CRUD (admin), provider profile management, search/filter API with pagination, portfolio photo uploads (local disk)

**Phase 4: Backend Booking Engine** — Full booking lifecycle (requested→quoted→accepted→in_progress→completed→paid→reviewed + cancelled/disputed branches), quoting, in-booking messages

**Phase 5: Backend Payments** — `PaymentProvider` interface, `MPesaSandboxProvider` implementation (STK Push mock, B2C mock), escrow logic, commission calculation, payout flow, payment history

**Phase 6: Backend Reviews, Disputes & Support** — Review creation (only from completed+paid bookings), auto-rating recalculation, dispute open/admin-resolve, support ticket CRUD

**Phase 7: Backend Admin APIs & WebSocket** — Dashboard KPI aggregation endpoints, drill-down filtered queries, Socket.IO event emission for all key events, activity log recording

**Phase 8: Seed Data & Docs** — 5 sample providers (2 verified, 1 pending, 1 rejected, 1 unverified), 3 customers, 10 bookings across all statuses, reviews, disputes, full README with setup steps

**Phase 9: Frontend Foundation** — Vite+React+TS+Tailwind setup, React Router, auth context, API service layer, i18next setup, responsive layout (navbar, sidebar, mobile nav), role-based routing

**Phase 10: Frontend Customer Flows** — Signup/login, home/search/browse, provider profile pages, booking request, quote acceptance, payment (sandbox M-Pesa mock UI), review writing, dispute opening

**Phase 11: Frontend Provider Flows** — Onboarding wizard, verification doc upload, service category selection, incoming booking management, quote submission, job completion marking, review responses, payout history

**Phase 12: Frontend Admin Dashboard** — KPI cards (auto-refreshing), activity feed (real-time via Socket.IO), bookings/revenue/category charts (Recharts), drill-down tables for disputes, verification queue, support tickets

**Phase 13: Frontend Support & Messaging** — In-booking message thread UI, support ticket creation/list/detail, dispute detail with evidence display

**Phase 14: i18n, Accessibility & Polish** — All strings extracted to locale files, Swahili skeleton file, WCAG contrast fixes, lazy image loading, bundle optimization

**Phase 15: End-to-End Verification** — Run both servers simultaneously, walk through all flows (signup → verify → search → book → quote → pay → review → dispute → admin resolve), fix any integration issues
